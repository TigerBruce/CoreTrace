# 统计口径

[返回首页](../README.md)

CoreTrace 把“系统报告的性能使用量”和“线程非空闲时间”分为两个选项。它们回答不同的问题，不能互相换算成剩余仿真速度。

## CPU

| 项目 | 任务管理器（Utility，默认） | 忙碌时间（Time） |
| --- | --- | --- |
| 数据源 | Windows PDH `% Processor Utility` | Windows PDH `% Processor Time` |
| 总体 | `Processor Information(_Total)` 的 Utility | 所有有效逻辑处理器 Time 的平均值 |
| 物理核心小图 | 同核心逻辑线程 Utility 的最大值 | 同核心逻辑线程 Time 的最大值 |
| 显示范围 | 0–100%，超出截为 100% | 0–100% |
| 含义 | 相对标称性能的使用量，包含性能状态的影响 | 采样区间内非空闲时间占比 |

Utility 原始计数器可以超过 100%，例如处理器在高于标称性能的状态下工作。CoreTrace 读取未截断值，再限制显示范围；总体先取 `_Total`，不把各核心截断值求平均。Microsoft 对该计数器的说明见 [CPU usage can exceed 100%](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/cpu-usage-exceeds-100)。

“忙碌时间 × 当前频率 / 基础频率”只能作为帮助理解 Utility 的简化模型，不能把某个 P 核与 E 核的频率相除，推导整颗 CPU 的准确上限。

### 为什么选择最忙线程

假设一个 P 核的两个逻辑线程分别是 100% 和 0%，该核心小图显示 100%。这表示至少有一个逻辑线程持续忙碌，适合观察串行任务；它不是物理核心所有执行单元的利用率。

如果两个逻辑线程都是 100%，小图仍为 100%。若两个线程轮流忙碌，本项目也没有计算它们非空闲时间的并集。该图无法证明“这个物理核心已经不可能再多做任何工作”。

### 与 Windows 比较

默认口径已在开发机与独立 Windows Utility 计数器对照。独立采样窗口、系统版本和取整仍可能造成差异。不要把“同口径”理解为每次刷新都保证数字完全相同。

比较时注明 Windows 版本、逻辑线程/物理核心视图、统计模式、历史范围以及负载阶段。任务管理器显示 100% 时仍能操作窗口，也不代表计数器错误：调度器可以在已有工作之间分配交互任务的运行时间。

## 温度与频率

- 每核温度来自受支持 Intel 型号的数字温度传感器 MSR，依赖 PawnIO；无法读取时留空。
- 每核频率根据读取到的倍频与估算基准时钟计算，属于采样时硬件频率，**不是包含睡眠时间的有效频率**。
- 总览“最高主频”是当前成功读取的核心频率最大值，不是厂商标称最大睿频，也不是全核平均值。
- 内存速率是启动时从固件信息读取的配置速率，单位 MT/s；它不是持续采样的内存控制器时钟，也不能直接称为同数值 MHz。

## 内存与进程

系统内存百分比按物理内存总量与可用量计算。前五列表按进程名称合并**私有工作集**，并以物理内存总量作为百分比的分母；没有把共享页重复相加。

列表柱形以当前第一名为满长，其他项目按相同比例绘制，因此两条柱的长度比例等于两者统计内存量的比例。它不是以整机内存为满长；右侧数值提供实际容量和系统占比。

界面以 MB / GB 标记容量，代码采用 1024 进制换算（MiB / GiB）。进程分组不等同于 Windows 的“应用”分组，不同名称的子进程会分别列出。

历史悬停中的应用 CPU 前五按进程 CPU 时间增量、经过时间及逻辑处理器数计算，始终是忙碌时间口径；不会随 Utility 切换而变成应用 Utility。

## 采样、历史和开销

后台采样线程使用低于普通线程的优先级，每轮等待约 1 秒后采样。采样耗时也计入实际间隔，因此它不是硬实时 1 Hz；繁忙时不会靠密集补采追赶时钟。

历史使用 70 帧环形缓冲区，保存两种 CPU 指标和每帧 CPU 前五；内存前五只保留当前列表。正常模式不持续保存遥测日志。源码包含显式诊断/验证入口，它们可在手动调用时产生本地文件。

渲染表面随像素面积扩大，核心数、进程数和透明模式也会影响开销。没有把开发机短时 CPU/内存采样当作所有电脑上的性能保证；欢迎提交注明环境与时长的测量结果。
